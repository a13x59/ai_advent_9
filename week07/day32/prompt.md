## Потенциальные баги

- **`get_payment` (строки 9–13): SQL-инъекция.** Значение `payment_id` подставляется в запрос через f-string: `f"SELECT * FROM payments WHERE id = '{payment_id}'"`. Любое значение вида `' OR '1'='1` или `'; DROP TABLE payments; --` ломает запрос. Это критично для сервиса платежей. Нужно использовать параметризованный запрос, как это уже сделано в `list_by_user` и `total`: `conn.execute("SELECT * FROM payments WHERE id = ?", (payment_id,))`.

- **`get_payment` (строки 9–13): утечка соединения.** Соединение `conn` открывается и никогда не закрывается (нет `conn.close()` и нет контекстного менеджера). При частых вызовах это приведёт к исчерпанию файловых дескрипторов / блокировкам SQLite. Сравните с `list_by_user`, где `conn.close()` есть.

- **`total` (строки 25–32): `SUM` возвращает `NULL` для пустой выборки.** Если у пользователя нет платежей, `fetchone()[0]` вернёт `None`, а не `0`. Метод обещает вернуть число (в `except` возвращается `0`), но в нормальном пути вернёт `None`. Это скрытый баг: вызывающий код, ожидающий число, получит `None` и, например, упадёт на арифметике. Нужно `COALESCE(SUM(amount), 0)` или обработка `None`.

- **`total` (строки 25–32): `except Exception: return 0` маскирует ошибки.** Проглатываются любые исключения (включая `sqlite3.OperationalError`, ошибки прав доступа, повреждение БД). Ошибка платежа превращается в «0», что может быть неотличимо от «нет платежей». Это критично для финансового домена — тихая потеря/искажение данных.

- **`total` (строки 25–32): утечка соединения.** Как и в `get_payment`, `conn` не закрывается ни в успешном пути, ни в `except`.

- **`list_by_user` (строки 15–23): утечка соединения при исключении.** `conn.close()` вызывается только после успешного `execute`/`fetchall`. Если запрос бросит исключение, соединение не закроется. Нужен `try/finally` или `with sqlite3.connect(...) as conn`.

- **`list_by_user` (строки 15–23): N+1 соединений.** На каждый `uid` открывается новое соединение и отдельный запрос. При большом `user_ids` это медленно и ресурсоёмко; логичнее один запрос с `IN (...)` или одно переиспользуемое соединение.

## Архитектурные проблемы

- **Репозиторий сам управляет соединениями.** `PaymentRepository` открывает/закрывает `sqlite3.connect` в каждом методе, дублируя логику и провоцируя утечки. Управление соединением (пул/фабрика/контекстный менеджер) должно быть вынесено наружу или инкапсулировано в одном месте.

- **Непоследовательная обработка ошибок.** `total` глушит все исключения, `get_payment` и `list_by_user` — нет. Единой политики обработки ошибок нет; поведение API непредсказуемо для вызывающего кода.

- **Непоследовательный стиль доступа к данным.** `get_payment` использует f-string, остальные методы — параметризацию. Это признак «legacy»-кода, но при ревью такое расхождение опасно: оно маскирует инъекцию как «стилевую» проблему.

- **Возврат «сырых» кортежей `SELECT *`.** `get_payment`/`list_by_user` возвращают позиционные кортежи без явного списка колонок. Любое изменение схемы таблицы молча ломает потребителей. Стоит явно перечислять колонки и/или маппить в доменные объекты.

## Рекомендации

1. **Исправить SQL-инъекцию в `get_payment`** — перейти на параметризованный запрос: `conn.execute("SELECT * FROM payments WHERE id = ?", (payment_id,))`. Это блокирующее замечание.
2. **Закрывать соединения гарантированно** — использовать `with sqlite3.connect(self.db_path) as conn:` во всех методах (или `try/finally`), чтобы исключения не оставляли открытые соединения.
3. **В `total` обработать `NULL`:** `SELECT COALESCE(SUM(amount), 0) ...` и убрать широкий `except Exception`. Если обработка ошибок нужна — ловить конкретные исключения (`sqlite3.Error`) и логировать их, а не возвращать `0` молча.
4. **Устранить N+1 в `list_by_user`:** один запрос с `WHERE user_id IN (?, ?, ...)` (с динамическим числом плейсхолдеров) и одним соединением.
5. **Явно перечислять колонки** вместо `SELECT *` и рассмотреть маппинг строк в доменные объекты, чтобы изоляция схемы БД не протекала в API репозитория.
6. **Добавить тесты** на: пустой результат `total` (ожидается `0`, а не `None`), попытку инъекции в `get_payment`, поведение при ошибке БД. Учитывая, что файл помечен как «демо с намеренными дефектами», стоит явно зафиксировать ожидаемые дефекты в тестах, чтобы правки не «случайно» их не устранили.
