Я изучил проект: main.py (FastAPI-бэкенд, стратегии контекста), storage.py (SQLite-хранилище) и index.html (веб-интерфейс). Ниже — конкретное предложение, как расширить агента моделью памяти из трёх слоёв, привязанное к уже существующему коду.

Что есть сейчас
Сейчас память у агента фактически двух видов, и выбор «куда сохранять» неявный:

Существующее	Что хранит	Аналог слоя
branches.messages	полная история диалога (по веткам)	краткосрочная
session_facts	ключ-значение факты (стратегия sticky_facts)	частично рабочая/долговременная
Проблемы: факты живут только внутри одной сессии, нет разделения «данные задачи» vs «знания навсегда», и сохраняется всё автоматически — пользователь явно не управляет, что и куда попадает.

Предлагаемая модель памяти (3 слоя)
Copy
┌─ Краткосрочная (short_term) ── текущий диалог
│    = messages активной ветки, окно N
│    живёт: пока идёт диалог
├─ Рабочая (working) ── данные ТЕКУЩЕЙ задачи
│    = цель, ограничения, TODO, промежуточные результаты, «сейчас делаем X»
│    живёт: пока задача/сессия активна
└─ Долговременная (long_term) ── профиль, решения, знания
     = имя, предпочтения, принятые решения, договорённости, факты о пользователе
     живёт: между сессиями, переживает «Новый диалог»
Ключевое отличие рабочей от долговременной — время жизни и область видимости: рабочая очищается вместе с сессией/задачей, долговременная — глобальная и переживает перезапуски и новые диалоги.

1. Изменения в storage.py — хранить отдельно
Добавить две отдельные таблицы (краткосрочная уже отдельно лежит в branches):

sql
Copy
-- Рабочая память: привязана к сессии/задаче
CREATE TABLE IF NOT EXISTS working_memory (
    entry_id   TEXT PRIMARY KEY,
    session_id TEXT NOT NULL,
    key        TEXT NOT NULL,
    value      TEXT NOT NULL,
    kind       TEXT NOT NULL DEFAULT 'note',   -- goal / constraint / todo / result / context
    importance INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    UNIQUE(session_id, key)
);

-- Долговременная память: глобальная, переживает сессии
CREATE TABLE IF NOT EXISTS long_term_memory (
    entry_id   TEXT PRIMARY KEY,
    key        TEXT NOT NULL UNIQUE,
    value      TEXT NOT NULL,
    kind       TEXT NOT NULL DEFAULT 'fact',   -- profile / decision / knowledge / preference / agreement
    tags       TEXT NOT NULL DEFAULT '[]',
    importance INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

-- Журнал явных решений (для отладки и прозрачности)
CREATE TABLE IF NOT EXISTS memory_log (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id TEXT,
    layer      TEXT NOT NULL,   -- short_term / working / long_term
    action     TEXT NOT NULL,   -- save / update / move / delete
    key        TEXT,
    source     TEXT NOT NULL,   -- manual / suggested
    created_at TEXT NOT NULL
);
Соответственно в класс HistoryStorage добавить in-memory кэши _working и _long_term (по аналогии с существующим _facts), методы:

load_working(session_id), save_working(session_id, entries), delete_working(session_id)
load_long_term(), save_long_term(entries)
move_entry(...) — перенос между слоями (например, «рабочая → долговременная», когда задача завершена и её решение надо запомнить)
list_memory(session_id) — отдаёт все три слоя одним объектом для UI.
Существующую session_facts можно оставить для обратной совместимости (стратегия sticky_facts), а новый слой long_term сделать надстройкой — либо мягко мигрировать session_facts → long_term_memory при первом запуске.

2. Явный выбор «что и куда сохранять»
Это главное требование. Предлагаю два режима, оба дают пользователю явный контроль:

А) Ручной (по умолчанию — ничего не сохраняется автоматически). В UI появляется кнопка «💾 в память» с выбором слоя. Отправка через API:

json
Copy
{
  "messages": [...],
  "memory_ops": [
    {"action": "save", "layer": "working", "key": "цель", "value": "написать отчёт", "kind": "goal"},
    {"action": "move", "from": "working", "to": "long_term", "key": "цель"}
  ]
}
Б) Авто-предложение с подтверждением (опциональный тумблер). По аналогии с уже существующей extract_facts() делаем suggest_memory(): модель возвращает JSON с кандидатами и предлагаемым слоем:

json
Copy
[
  {"key": "имя_пользователя", "value": "Иван", "layer": "long_term", "kind": "profile", "reason": "..."},
  {"key": "текущая_цель", "value": "рефакторинг storage.py", "layer": "working", "kind": "goal"}
]
Эти кандидаты не сохраняются сразу, а возвращаются как pending_memory — UI показывает карточки, и пользователь жмёт «✅ сохранить / ❌ отклонить / переместить в другой слой». Только подтверждённое пишется в БД и логируется в memory_log. Это ровно «вы явно выбираете, что и куда сохраняется».

3. Изменения в main.py
Расширить AgentRequest полями:

memory_ops: List[dict] = [] — явные операции сохранения/переноса/удаления.
auto_suggest_memory: bool = False — включить режим предложений.
Добавить suggest_memory() рядом с extract_facts() (те же call_deepseek_raw, parse_json_object, подсчёт стоимости — структура уже готова, можно переиспользовать).

Переписать build_request_messages() так, чтобы системный промпт собирался из всех трёх слоёв:

python
Copy
def build_request_messages(strategy, conversation, working, long_term, window_size):
    sys_parts = []
    if long_term:
        sys_parts.append("Долговременная память:\n" + memory_to_text(long_term))
    if working:
        sys_parts.append("Рабочая память (текущая задача):\n" + memory_to_text(working))
    messages = []
    if sys_parts:
        messages.append({"role": "system", "content": "\n\n".join(sys_parts)})
    messages.extend(conversation[-window_size:])
    return messages
Здесь краткосрочная память — это окно conversation[-window_size:], рабочая и долговременная идут системным блоком. Это делает влияние каждого слоя измеримым: можно сравнивать ответы «без памяти / только рабочая / рабочая + долговременная».

Новые эндпоинты:

GET /agent/{session_id}/memory → все три слоя (для восстановления UI).
POST /agent/{session_id}/memory → применить memory_ops.
POST /agent/{session_id}/memory/suggest → получить кандидатов.
POST /agent/{session_id}/memory/move → перенос между слоями.
DELETE /agent/{session_id}/memory/{layer}/{key}.
GET /memory/longterm → глобальный список долговременной памяти (видна во всех сессиях).
GET /agents и сводка контекста дополнить счётчиками памяти: working_count, long_term_count — чтобы в UI видеть, что попало в каждый слой.

4. Изменения в index.html
Новая панель «Память» (три вкладки/колонки: Краткосрочная / Рабочая / Долговременная). Каждая показывает свои записи: ключ, значение, kind, важность, дату.

Явное сохранение: у каждого сообщения в чате — кнопка «💾», раскрывающая выбор слоя (working / long_term); либо общий блок ввода «ключ → значение + слой».

Очередь предложений (когда включён auto_suggest_memory): карточки pending_memory с кнопками сохранить/отклонить/сменить слой.

Индикатор того, что ушло в промпт: в renderContext добавить строки вида «Отправлено: рабочая память (3) + долговременная (5) + окно 5».

5. Как это влияет на ответы (проверочные сценарии)
Сценарий	Что демонстрирует
Новый диалог, спрашиваю «как меня зовут?»	Долговременная память возвращает имя — значит профиль пережил сброс сессии
Длинная задача, окно уже уехало	Рабочая память держит цель/ограничения — ответ не «забывает» контекст задачи

Отклоняю предложение модели	Ничего не пишется в БД — полный контроль
